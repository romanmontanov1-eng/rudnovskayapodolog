# Проверка авторизации, 26 ноября 2026

## Наблюдения на работающем Worker

Проверялся https://olga-works.romanmontanov1.workers.dev/ без настоящего пароля и без публикаций. Реальные секреты не читались.

| Запрос | Фактический статус | Фактическое тело |
| --- | --- | --- |
| GET /api/works без cookie | 401 | {"error":"Войдите в кабинет."} |
| POST /api/login, неверный ASCII-пароль, правильный Origin | 401 | {"error":"Неверный пароль."} |
| POST /api/login, неверный кириллический пароль, JSON UTF-8 | 401 | {"error":"Неверный пароль."} |
| POST /api/login, Origin: null | 403 | {"error":"Запрос отклонён."} |
| POST /api/login, тело `{`, правильный Origin | 502 | {"error":"Не удалось выполнить запрос. Поля сохранены — попробуйте ещё раз."} |

Content-Type у этих ответов — application/json. Тело ответа с неверным паролем — 42 байта; UTF-8 и JSON декодировались без ошибки. Главная и app.js отвечали 200 с charset=utf-8 и Cache-Control: no-store. Развёрнутый app.js соответствует версии main до исправления. Конфигурация main уже использует ratelimits.simple; два тестовых неверных пароля вернули 401, а не ошибку лимитера. Проверить секреты или успешный вход на production без пароля невозможно, пароль в чат не запрашивается.

## Подтверждённые дефекты

1. Клиент называл любой сбой response.json() «Ответ сервера получен не полностью». Даже целый HTML 502 от прокси получал это сообщение. Само сообщение не доказывает обрыв JSON или проблему UTF-8.
2. Клиент связывал успешный login и последующий home()/GET works одним сценарием на форме входа. При ошибке GitHub уже выданная сессия выглядела как неудачная авторизация. Начальная загрузка также отправляла на login при любой ошибке, а не только 401.
3. Ошибка JSON запроса, отказ LOGIN_LIMITER и ошибки GitHub проходили через общий catch с 502. Было невозможно отличить отказ авторизации GitHub от транспортного сбоя.
4. Отсутствующий LOGIN_LIMITER раньше пропускался. Теперь вход при отсутствии/отказе защиты закрывается с JSON 503; защита не отключена.

Это подтверждённые причины неправильной диагностики и отдельная ошибка HTTP-статуса. Исходный сетевой сбой Safari (если fetch действительно отклонён) пока не воспроизведён и не доказан. Нельзя утверждать, что его причина — кириллица, cookies, Origin или лимитер.

## Изменения

- API-клиент сохраняет путь, HTTP-статус, тип ошибки и request ID, различает сеть/timeout/HTML/некорректный JSON/отказ HTTP; читает тело один раз. Cookies передаются явно через credentials:same-origin. Авторизация не повторяется автоматически.
- GET /api/session проверяет cookie без обращения в GitHub. Сбой списка работ не сбрасывает валидную сессию. Структура страниц, CSS и публичные страницы не изменяются.
- API возвращает JSON в явно заданном UTF-8, no-store и nosniff. Неверный JSON входа — 400, неверный пароль — 401, чужой/отсутствующий Origin — 403, Content-Type — 415, лимит — 429 с Retry-After, недоступная защита — 503.
- Cookie остаётся HttpOnly/Secure/SameSite=Strict, Path=/, срок 12 часов. Некорректная/поддельная/истёкшая cookie даёт 401. Пароль не обрезается и не нормализуется. Смена ADMIN_PASSWORD отзывает прежние сессии.
- Ошибки GitHub получают отдельные коды GITHUB_AUTH/ACCESS/NETWORK/RESPONSE, не раскрывая токены или upstream-тело. Логи содержат только requestId, path, status, code — без пароля, cookie и тела запроса.

## Проверка и деплой

16 тестов: 10 auth/client/UI + 6 прежних публикации. Проверен также generated worker.mjs: маршруты JS-модуля, UTF-8, login и session. Фикстуры искусственные, production не изменяется.

Команды: `node _cabinet/tests/auth.test.mjs`, `node _cabinet/tests/publication.test.mjs`, `node _cabinet/build.mjs`.

Для Cloudflare сохраняются build command `node _cabinet/build.mjs` и deploy command `npx wrangler deploy --config _cabinet/wrangler.toml`. LOGIN_LIMITER и ratelimits.simple остаются. После деплоя открыть основную HTTPS-ссылку в Safari заново, войти, проверить GET session и GET works, затем перезагрузку и выход. Если останется ошибка, записать только статус, код и X-Request-ID/CF-Ray и сопоставить с Workers Logs. Не передавать пароль, cookie или токен.

Настоящего iPhone в среде нет. Полный успешный вход с реальными production-секретами и причина исходного сбоя Safari остаются неподтверждёнными до проверки на устройстве. Обновление подготовлено в отдельной ветке, без деплоя и без изменения публичного сайта.
