# Проверка запуска на опубликованном адресе, 26 ноября 2026

Адрес: https://olga-works.romanmontanov1.workers.dev/. На момент проверки PR 2 слит и развёрнут, main fa8894947133dd2ca6d3efaa16bca5e7696c214e. Секреты не использовались. Вход проверялся только заведомо неверным диагностическим паролем; работы не публиковались.

## Что фактически проверено

- Реальный Chrome: HTML и JS загружаются, форма видна, нажатие «Войти» вызывает API и показывает «Неверный пароль».
- Реальный WebKit 26.5 (Playwright), профиль iPhone 13, ширина 390 px: опубликованные /, app.js, api-client.mjs, CSS и manifest — 200 с правильными MIME и no-store; GET /api/session — 401; кнопка отправляет настоящий POST /api/login, сервер отвечает JSON 401. Ошибок JS и сетевых отказов нет.
- В чистом профиле нет service worker controller, регистраций service worker и Cache Storage. В исходниках service worker не регистрируется. Это не доказывает отсутствие старого кеша/контроллера на конкретном устройстве владельца.
- В WebKit выполнены проверки с перезагрузкой и искусственными отказами загрузки/IndexedDB. Результаты сохранены в tests/reports. Тесты не записывают пароль, cookies, токены или тела запросов.

## Подтверждённые дефекты и границы диагноза

1. В опубликованной форме не указаны method/action. Если JS-обработчик отсутствует, браузер по умолчанию выполняет GET текущего документа. В тесте обработчик искусственно снят после обычного запуска: нажатие вызвало GET / и не вызвало POST /api/login. Таким образом, один лишь GET / со статусом 200 не доказывает попытку входа.
2. Запуск всего приложения зависел от дополнительного импорта api-client.mjs. При искусственной блокировке этого модуля ни обработчик формы, ни GET session не запускаются. В опубликованном HTML при этом нет сообщения об ошибке загрузки; секции скрыты. На устройстве пользователя форма видна — поэтому именно отказ импорта там НЕ доказан.
3. IndexedDB открывалась сразу на старте, ещё до входа. Запуск авторизации не должен зависеть от доступности хранилища черновиков.

Чистый WebKit не воспроизвёл исходный сбой устройства владельца. Удаление обработчика и блокировка модуля — fault injection, а не наблюдение этих событий на его iPhone. Точная причина потери/неотправки запроса на этом устройстве остаётся неустановленной без текста ошибки, версии iOS и контекста открытия. Не заявлять, что service worker, VPN или несовместимость Safari доказаны как причина.

## Исправление

- build.mjs собирает helper и приложение в один classic defer-скрипт, без браузерного import-графа. URL app.js содержит SHA-256 версию содержимого. Заголовки no-store сохранены. Старый URL helper продолжает обслуживаться для ранее загруженных страниц.
- Кнопка входа disabled в HTML; она включается только после назначения submit-обработчика. Форма явно method=post/action=/api/login, поле пароля имеет name. Значение пароля никогда не попадает в URL. При утрате обработчика нативный POST отклоняется прежними проверками Origin/JSON (в WebKit получен 403; при правильном Origin и неверном Content-Type — 415), а не вызывает молчаливый GET /.
- До старта JS виден текст загрузки и инструкция; без JavaScript — noscript-пояснение. При пустом пароле показано объяснение native validation. При submit сразу показано «Проверяю пароль…». Основная разметка, CSS и оформление не менялись.
- IndexedDB инициализируется лениво при работе с черновиками. Проверка сессии и кнопка входа работают и при запрете IndexedDB.
- fetch вызывается с корректным глобальным получателем. Сетевая ошибка содержит только безопасные путь endpoint и NETWORK, без данных запроса.

## Проверки исправления

18 Node-проверок: 10 auth + 6 publication + 2 startup; проходят. Дополнительно WebKit:
- Кандидат HTML/JS подставлен в браузере поверх настоящего production origin; API login/session остаются живыми production API. Это браузерная проверка кандидата, НЕ его деплой.
- Заблокирован старый api-client.mjs, запрещена IndexedDB: кнопка включается, пустой пароль не отправляется, тестовый неверный пароль вызывает настоящий POST login/401, ошибок JS нет.
- Повторная загрузка работает; нет SW и Cache Storage в профиле.
- Отказ main app.js оставляет кнопку disabled и видимое объяснение загрузки.
- Искусственная утрата submit-обработчика у кандидата: POST login/403; нет возврата на GET /.

Запуск: `node _cabinet/build.mjs`, `node --test _cabinet/tests/*.test.mjs`. Браузерные проверки: установить официальный Playwright и WebKit, затем `node _cabinet/tests/browser-startup.cjs`. PLAYWRIGHT_MODULE допускает путь к установленному Playwright, OLGA_REPORT — путь JSON отчёта. OLGA_REPRO_LEGACY=1 включает исторические fault-injection проверки против версии до этого патча; после деплоя патча их включать не нужно. Системные библиотеки WebKit в этой среде загружались из официального Debian и извлекались в рабочую папку без изменения системы.

Дизайн, публичный index.html/works.html, серверные проверки Origin, cookie, LOGIN_LIMITER и права GitHub не изменены. Настоящего iPhone нет, Linux WebKit с профилем iPhone не заменяет устройство. Полный успешный вход с реальным production-паролем не проверялся. Ветка подготовлена для деплоя; main и активный Worker этим патчем не обновлялись.
